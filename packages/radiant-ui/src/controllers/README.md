# Controllers and helpers

The reusable primitives components are built from. Read this table before writing bespoke logic: most behaviors a new component needs already exist as a tested controller or helper.

Two entries, both tree-shakeable (a bundle contains only what it imports):

| Import path                        | Holds                                                                                                                                     |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `@ecopages/radiant-ui/controllers` | `controller`: stateful classes attached to a host, with `createX` factories, plus the DOM utilities they are built from. Needs a browser. |
| `@ecopages/radiant-ui/helpers`     | `helper`: pure functions and types. No DOM at import time, so they run on the server and in tests. Dates, masks, numbers, ordering math.  |

Entry sources: [`../controllers.ts`](../controllers.ts) and [`../helpers.ts`](../helpers.ts). They are named so the package `sideEffects` entry for built `index.js` files does not match them.

Contract, `Controller`, `bindController`, compose-or-extend and the protected hooks: [Controllers in the catalog README](../components/ui/README.md#controllers).

## Composing a component from primitives

1. Name the behaviors: open and close, keyboard movement, dragging, filtering, date math, positioning.
2. Pick one primitive per behavior from the tables below. Controllers own the DOM wiring; helpers own the decisions and formatting.
3. Hold the controllers in fields of the custom element with `createX(this, config)`. Config is getters (`getItems`, `getTarget`) and callbacks (`onChange`), so the element keeps its own state and the controller never reaches into it.
4. Keep what is specific to the component (state, markup, `rui-change` events) in the component. Use a helper, not a controller, for anything that only maps input to output.
5. If a decision needs to differ, use a config callback first, a documented `protected` hook by subclassing second, a new controller last.

Example, "a calendar with draggable events and a filter":

- Month grid, selection, headers: `buildCalendarMonth`, `getWeekdayLabels`, `formatMonthYear`, `addMonths`, `toggleMultipleIso` or `advanceRangeSelection` (`helper`).
- Arrow keys across the day cells: `createRovingController` with all days as one flat list and `orientation: 'none'`, moving by your own row and column math, or `navigateRovingTabindex` for one axis (`controller`).
- Dragging an event to another day: `createSortableController` with a `SortableGroup` shared by the day containers (`controller`), or `createPointerDragController` with `elementUnderPointer()` for free-form drops, then `dateToIso` for the target day (`controller`, `helper`).
- Filtering events by text: `textContains` (`helper`).
- Event details in a popup: `createPopoverController` (`controller`).
- Re-render when events are added: `createMutationController` (`controller`).

### Audio visualizer presets

A preset implements `AudioVisualizerPreset` (`fftSize?`, `smoothing?`, `mount(target)`, `draw(frame)`, `rest()`, `destroy()`); the `AudioFrame` buffers are reused every frame, so a preset reads them in `draw()` and keeps nothing. Presets are factory functions, so a bundle contains only those it imports. Canvas presets create an `aria-hidden` canvas in the target (which needs a height and no other content), follow the canvas's own size and the device pixel ratio, and read `color` (a custom property name such as `--primary`, the default, or any CSS color) at draw time so they follow the theme. Types exported with them: `AudioFrame`, `AudioVisualizerPreset`, `AudioVisualizerState`, `AudioVisualizerControllerConfig`, `BarsOptions`, `BarsDomOptions`, `BarsCanvasOptions`, `WaveOptions`, `FrequencyBand`.

#### Writing a preset

The contract, in the order the controller calls it:

- `mount(target)` once the preset is in use: when the controller attaches, or on the first `play` if the target was not there, and from `setPreset`. It can run again on the same object after `destroy()`. Create what the preset needs inside `target` here, and nothing outside it.
- `draw(frame)` on every animation frame while the media plays (or a stream is set), the context runs, motion is not reduced and `getEnabled` allows it. `frame` is `{ frequency, waveform, sampleRate, fftSize }`: the analyser's bytes, 0 to 255, `fftSize / 2` frequency bins of `sampleRate / fftSize` Hz, and `fftSize` waveform samples centered on 128. The buffers are reused, so read them and keep nothing.
- `rest()` when the loop stops (pause, end, stream changed or `null`, context suspended) and instead of `draw()` under `prefers-reduced-motion` (the state is `reduced`) or while `getEnabled` is `false`. Show a static, sensible idle look, or nothing. It can run on a preset that was never mounted.
- `destroy()` when `setPreset` replaces the preset (after its `rest()`) and when the controller is destroyed. It must remove what `mount` added and leave no listener, observer or timer.
- `fftSize` (a power of two, 32 to 32768, default 1024) and `smoothing` (0 to 1, default 0.8) are read when the loop starts and when the preset is swapped while it runs.

Keep `draw()` cheap: allocate nothing per frame (reuse arrays and objects, as `stepPeak` does), read the canvas size from `surface.width` and `surface.height` and never from the DOM, and take colors from custom properties through `surface.resolveColor('--primary')`, once per frame, so a theme change shows on the next frame; hard-coded colors do not follow a theme. A preset can also be DOM-based: `bars({ mode: 'dom' })` writes a custom property on elements the host rendered and removes it on rest. Publish a preset as a factory that returns an `AudioVisualizerPreset` (`export function spectrum(options): AudioVisualizerPreset`) from a package that imports only `@ecopages/radiant-ui/controllers` and lists `@ecopages/radiant-ui` as a peer dependency; the usual name is `radiant-visualizer-<name>`. There is no preset registry and no lookup by name: the host imports the factory and passes it to `preset` or `setPreset`.

Not stable yet: `AudioFrame` may gain fields (a timestamp, say), `mount` may receive options, and the helper signatures (`stepPeak`, `segmentBounds`, the `onResize` argument) may change in a minor release. A preset that needs only the fields above and the lifecycle is the safest to write.

## Accessibility: what each controller does and what you must provide

Controllers handle behavior, not semantics. Per-controller pages in the docs app list the same in full.

- Modal pattern (`FocusTrapController`, `ScrollLockController`, `PortalController`, `DismissController`): you provide `role="dialog"`, `aria-modal="true"`, an accessible name and an `inert` or `aria-hidden` background. The trap loops over visible, non-inert, enabled focusable elements only (`getFocusable` overrides).
- `DismissController`: Escape reaches one layer per key press (the nested one first), is ignored while composing, and a window blur or tab switch is not focus leaving. An Escape whose default a handler already prevented reaches no layer, so a widget that handles Escape itself must prevent it only when it did something. `onDismiss` returns `false` to decline: the key then goes to the next layer. Focus return and `aria-expanded` are yours in `onDismiss`.
- `HotkeyController`: skips keys typed in a text field, while composing and with a default already prevented; Alt is never matched, `mod` is Meta or Ctrl. Scope single-character keys to an element with `getTarget` instead of `document` (WCAG 2.1.4; a screen reader's browse mode swallows them elsewhere). `aria-keyshortcuts` and any visible key label are yours.
- `PopoverController`: sets no `aria-expanded`, `aria-controls` or `aria-haspopup` and manages no focus. With the default `portal: true` the popup goes to `getPortalContainer`, else into the nearest `[aria-modal="true"]` or modal `<dialog>` ancestor of the anchor (so it stacks above a modal), else to the end of `document.body`. `getFloating` need only find the popup where it lives in the owner; a portaled popup is outside the owner, so `getFloatingElement()` returns `getFloating()`, else the portal's mounted node (so through the exit transition), else `null`; it caches nothing. Read the popup from `getFloatingElement()`, not from a cached lookup.
- `PopoverController` and Tab: a popup at the end of `document.body` is skipped by Tab from the trigger, so use `portal: false` or move focus in on open; one inside a modal surface joins the modal's Tab order at the end of the surface.
- `attachFloating` and `applyFloatingPosition` convert for an ancestor that is the containing block of fixed elements (`transform`, `filter`, `contain`, `will-change`), and re-position when a transition ends on an ancestor.
- `PortalController`: moving a node re-runs `connectedCallback` of custom elements inside it.
- `RovingController`: ignores Alt, Ctrl and Meta keys and keys typed in a text field that is not an item (checkboxes, radios, buttons, ranges and selects stay navigable; an input that is an item still navigates); Shift does not stop it; arrows are not flipped for RTL; you own `aria-selected` and `aria-current`. An `li` without a `tabindex` attribute reports `tabIndex` `-1`, so give rows `tabindex="-1"` in the markup.
- `SortableController`: provide a live region with `announce`, focusable items with a role, `aria-roledescription` and instructions, a non-drag alternative (`move` and `moveBy` behind buttons), `touch-action: none` on the handle, a 24px target and focus restored after a drop. Escape cancels a pointer drag. With `preview` in an `aria-modal` dialog return a layer inside the dialog from `getPreviewLayer`.
- `SwipeController`, `PointerDragController`: pointer-only; provide a button and keyboard alternative (WCAG 2.5.1).
- `MenuTreeController`: `menuitem`, `menuitemcheckbox` and `menuitemradio`, also inside a `role="group"` within the menu; only a `menuitem` can own a submenu; no typeahead; Escape closes the focused submenu only; you own `role="menubar"` or `menu` and the label.
- `setCollectionActive`: sets `aria-activedescendant` and `data-active`, with a stable unique `id` per option; you own `role="option"`, `aria-selected` and `aria-expanded`.

## Internal

Not exported from either entry; do not import them from `dist` or `src` in consumer code.

- `ListboxHost` (`components/ui/shared`): reads `RuiListbox` host types from the catalog.
- `ListboxPopoverController` and `CalendarPopoverController` (`components/ui/shared`): they encode select and combobox key policy and the calendar's day markup, so no public API yet.
- `preview-timing`, `field-label` and `form-owner` in `components/ui/shared`: catalog-specific. `multi-value` lives in `src/lib`, and the form state logic in `src/lib/form`.

## Adding a primitive

Add the export to `src/controllers.ts` or `src/helpers.ts`, give it TSDoc with a short `@example` where the usage or result is not obvious (controllers: the `createX` call; helpers: an input and output line), and add a row here. A pure module goes in `helpers`; anything that touches the DOM when called goes in `controllers`.
