`rui-form` can drive a form state store it did not create. Set the new `store` property to a `FormStateStore` and the form becomes a control bridge: control changes call `setValue`, blur calls `blur`, submit writes every control value that differs from the store and awaits `validate()`, and native control validity is re-read from the controls and sent through `setErrors('native', ...)`. The store owns validation timing, touched and dirty state, defaults and which errors show, so `mode`, `revalidate-mode`, field `defaultValue`, `defaultValues`, `resolver` and field `rules` are ignored while a store is injected. Without `store` the form behaves as before.

`FormStore` implements `FormStateStore` and gains `getValue`, `getSnapshot`, `blur`, `validate` and `setErrors`. Type and behaviour changes to know: `FormContextValue.store` is widened from `FormStore` to `FormStateStore`, so code that reads `FormStore`-only members such as `getValues()` from the context must narrow with `instanceof FormStore`; `FormStore.errors` is now an accessor, so a subclass that declares `errors` as a property no longer compiles; and a built-in submit is blocked by an error from any `setErrors` source until the source clears it.

Two fixes ship with it. A `rui-field` no longer unregisters and registers again on its first name update, which briefly dropped its value from the built-in store; a real rename now moves the field through the new `FormContextActions.renameField` in one notification. And a submission always settles: `FormStore.isSubmitting` stays true until an awaited `onSubmit` finishes and is always cleared, a validator that throws ends the submission with `rui-invalid` whose `detail.error` holds the thrown value, and an `onSubmit` rejection is reported with `reportError` instead of becoming an unhandled rejection.
