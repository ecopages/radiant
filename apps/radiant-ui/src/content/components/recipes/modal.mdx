# Modal dialog

<p class="docs-lede">
	A dialog that holds focus and the page still while it is open, and gives both back when it closes.
</p>

## Goal

A confirmation, a form in an overlay or a lightbox: while it is open the user works only in the dialog. Tab loops inside it, what is behind does not scroll, Escape or a press outside closes it, and focus goes back to the button that opened it, or to the next place the work leads when the dialog's action removed that button.

## Primitives

- [PortalController](/docs/controllers/portal) moves the dialog out of the element it lives in and puts it back on close, so no overflow or stacking context of its parents clips it. Without `getContainer` it goes to `document.body`; the example passes the example frame instead, so the dialog stays inside it and the frame styles still apply. It also carries the theme of the place it left.
- [FocusTrapController](/docs/controllers/focus-trap) moves focus into the dialog on attach, loops Tab and Shift+Tab inside it, and returns focus on destroy: to the previously focused element, or to the control `getReturnFocus` names. The example uses both: Cancel and Escape leave it to the default, and Delete removes the row that opened the dialog, so `getReturnFocus` names the Delete button of the next row (the previous row for the last one, or Reset when none is left).
- [ScrollLockController](/docs/controllers/scroll-lock) stops the page from scrolling, and counts, so two modals open at once release it only when both are closed. This site is an app shell where the article column scrolls and the document does not, so the example passes that column as `getTarget`; without `getTarget` it locks the page, which is what you want in a project whose page scrolls.
- [DismissController](/docs/controllers/dismiss) reports Escape and a press outside the dialog. Focus leaving is not listened to, because the trap already keeps it inside.

Left to the recipe: the list and which row is pending, the open and close functions that attach and destroy the four together, choosing where focus goes after a delete, and `aria-modal` and a label on the dialog. None of them makes the rest of the page `inert`; a modal that must also block the pointer on the page or find-in-page sets `inert` itself.

Escape stays with DismissController: its `onDismiss` closes the dialog, and the close calls `trap.destroy()`, which is where `getReturnFocus` is read. The trap has no Escape of its own. For a non-modal surface, such as an inline panel that should hold focus only while the user works in it, pass `getEnabled: () => false` (or a getter that reads the panel's state) so Tab can leave without detaching the trap; this dialog is modal and leaves it out.

## Example

Press Delete on a file: the example frame dims behind the dialog. Press Tab to see focus stay inside, then close it with a button, Escape or a press on the dimmed area. Cancel, Escape and a press outside keep the file and return focus to its Delete button. Delete in the dialog removes the file and moves focus to the Delete button of the next file through `getReturnFocus`; delete the last one and focus goes to Reset, which restores the list. The status line says what happened. Pick an authoring pattern below; they all behave the same, and the one you pick is remembered on the other recipes.

<RecipePattern id="element">

The same behavior as a `RadiantElement`. The markup is authored inside the element and the element finds its parts with `@query`; there is nothing to mount, clean up or run again.

The four controllers are built directly because the dialog starts and stops them, and the `@onEvent` listeners keep working after the layer is portaled because the container is the element itself. The cleanup callback closes the dialog if the element is removed while the dialog is open. What the Radiant form removes: the `mount` function and its registration, the cleanup to return and call, and the re-run after a client-side navigation.

</RecipePattern>

<RecipePattern id="component">

The same dialog as one self-contained tag. The element owns its markup: it keeps the files and the file being deleted as state and draws the list, the dialog and the status line with `render()`, so there is no markup to author or copy and the page holds only the tag.

<PrimitiveExample host>
	<modal-app></modal-app>
</PrimitiveExample>

<RecipeCode recipe="modal" pattern="component" />

The dialog is open while `pending` names a file, so the click handlers only write state: asking sets `pending`, and Cancel, Escape, a press outside and Delete clear it. The controllers start and stop in `updated()`, after the render that shows or hides the layer. That order is what makes the focus rules work without a manual step: the layer is visible when the trap looks for something to focus, and the list is already redrawn when `getReturnFocus` looks up the Delete button of the next file, or Reset when none is left, by attribute instead of holding a node that the render replaces.

Compared with the Radiant element above, the data is state you can change and the focus targets are found from it, but restyling the structure means editing the class. The layer is portaled into the element and put back on close, so the render must find it again where the controller left it; the element keeps the layer in one place in its markup and never keys it away. It also needs the render path on the server to have content before the script runs: this docs build prerenders the tag empty and the client draws it, so the page shows nothing until the script loads, which a page of authored children does not.

</RecipePattern>

<RecipePattern id="controller">

The same behavior as a `RadiantController` attached to markup that already exists. The markup carries `data-controller="modal"` and the class finds its parts with `@query`, exactly as the element does.

<RecipeExample recipe="modal" pattern="controller" />

<RecipeCode recipe="modal" pattern="controller" />

There is no custom element tag to define, so the markup can come from a server template or a CMS and stay plain HTML until the controller attaches. One registry the docs site starts over the document connects `data-controller="modal"` elements, including ones inserted later, and disconnects the ones that are removed. The class only registers itself with `@controller('modal')`. The four controllers are still built directly, and the cleanup callback closes the dialog, restores the scroll lock and the portaled layer when the element is removed while the dialog is open. Differences from the element form: the root is reached through `this.host` instead of `this`, and `connect()` replaces `onConnected()`.

</RecipePattern>

### Styles

The layer is positioned with `inset: 0` against the nearest positioned ancestor, here the example frame, dims what is behind and centers the dialog. Use `position: fixed` to cover the whole page. The stylesheet is the `modal.css` tab in the files above.
