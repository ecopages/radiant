# Popover menu

<p class="docs-lede">
	A button that opens a menu beside it, walked with the arrow keys and closed with Escape or a press outside.
</p>

## Goal

An actions menu on a row, a card or a toolbar. Opening moves focus into the menu, the arrow keys move between items, and every way of closing it ends with focus back on the button that opened it when the user did not choose to go elsewhere.

## Primitives

- [PopoverController](/docs/controllers/popover) shows the panel beside the button and keeps it positioned. With `onDismiss` set, it also reports an outside press, focus leaving and Escape through a [DismissController](/docs/controllers/dismiss) it owns, so the recipe does not add a second one. `portal: false` keeps the panel where it is.
- [RovingController](/docs/controllers/roving) gives the menu items one tab stop and moves it with the arrows, Home and End.

Left to the recipe: the open flag, moving focus into the menu on open, and returning focus to the button. The popover reports why it was dismissed and does not restore focus, because that depends on the reason: after Escape or choosing an item the button gets focus, after a press elsewhere the press already moved it.

## Example

Open the menu with the button, move with the arrow keys, choose with Enter, or press Escape to close it. Pick an authoring pattern below; they all behave the same, and the one you pick is remembered on the other recipes.

<RecipePatterns patterns={['element', 'component', 'controller', 'plain']}>

<RecipePattern id="element">

The same behavior as a `RadiantElement`. The markup is authored inside the element and the element finds its parts with `@query`; there is nothing to mount, clean up or run again.

<RecipeExample recipe="popover-menu" pattern="element" />

<RecipeCode recipe="popover-menu" pattern="element" />

`createPopoverController(this, ...)` and `createRovingController(this, ...)` are held in fields because the element calls them when the menu opens; both attach when the element connects and are destroyed when it disconnects, as are the `@onEvent` listeners. The popover still reports the dismissal reason, so the element decides whether focus returns to the button. `sync()` goes in `onConnected` because the items exist only after the element has its children.

What the Radiant form removes: the `mount` function and its registration, the cleanup to return and call, and the re-run after a client-side navigation.

</RecipePattern>

<RecipePattern id="component">

The same menu as one self-contained tag. The element owns its markup: it keeps the open flag and the status as state and draws the button, the menu and the status line with `render()`, so there is no markup to author or copy and the page holds only the tag.

<PrimitiveExample host>
	<popover-menu-app></popover-menu-app>
</PrimitiveExample>

<RecipeCode recipe="popover-menu" pattern="component" />

`open` and `status` are `@state`, so `aria-expanded`, `hidden` and the status text follow from `render()` and `setOpen` no longer writes them. The controllers still read the live DOM, so they look the button, the menu and the items up with `querySelector` in their getters instead of holding `@query` fields. The popover shows the menu in `sync()`, ahead of the render, so focus can move into it at once; `updated()`, which runs after each commit, attaches and syncs the roving controller to the menu the render produced. The status line is bound with `this.$.status`, so announcing patches one text node.

Compared with the Radiant element above, the markup lives inside the element, so there is nothing to keep in step with the page and the labels are data you can change, but restyling the structure means editing the class. It also needs the render path on the server to have content before the script runs: this docs build prerenders the tag empty and the client draws it, so the page shows nothing until the script loads, which a page of authored children does not.

</RecipePattern>

<RecipePattern id="controller">

The same behavior as a `RadiantController` attached to markup that already exists. There is no custom element tag: the root is a plain `div` carrying `data-controller="popover-menu"`, and the class finds its parts with `@query` just as the element does.

<RecipeExample recipe="popover-menu" pattern="controller" />

<RecipeCode recipe="popover-menu" pattern="controller" />

The class is registered with `@controller('popover-menu')` and nothing in the file starts it: one registry the docs site starts over the document attaches it to every `data-controller="popover-menu"` element, including markup inserted later, and disconnects it when the element is removed. `createPopoverController(this, ...)` and `createRovingController(this, ...)` accept the controller as their host, so they attach on connect and are destroyed on disconnect, as are the `@onEvent` listeners.

Compared with the Radiant element, there is no tag to define, so the markup can come from a server or a CMS and only needs the attribute. The differences are small: the controller has no `onConnected`, so the first `roving.sync()` goes in a connected callback registered in the constructor, and something outside the class has to start the registry.

</RecipePattern>

### Styles

The menu hides with `hidden` and sits in the flow under the button; add `position: absolute` to float it over what follows. The stylesheet is the `popover-menu.css` tab in the files above.
