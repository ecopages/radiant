# Calendar of events

<p class="docs-lede">
	A month of days, each holding events you can drag to another day, and a filter that narrows them.
</p>

## Goal

Reach for this shape for a planner, a schedule or a board whose columns are dates. The page imports only from `@ecopages/radiant-ui/controllers` and `@ecopages/radiant-ui/helpers`.

## Primitives

- [`buildCalendarMonth`, `getWeekStartsOn`, `getWeekdayLabels`, `formatMonthYear`, `formatDisplayDate`](/docs/helpers/intl-date) build the weeks, the week start, the headers and the day names for the locale, so the grid has no date arithmetic of its own.
- [`textContains`](/docs/helpers/text-filter) decides which events match the filter, ignoring case and accents.
- [`SortableController`](/docs/controllers/sortable) with one [`SortableGroup`](/docs/controllers/sortable#moving-between-lists) makes every day a container events move between. It handles the pointer drag, the keyboard path (Space lifts, the arrows move within the day, PageDown and PageUp move to the next and previous day) and the announcements. It never moves a node: `onChange` applies the move to the owner's list of events and renders again.
- [`RovingController`](/docs/controllers/roving) keeps the days to one tab stop. With `orientation: 'none'` it handles no keys, so the script maps the arrows to a step of one day or one week and calls `focus()`.

The recipe decides three things itself: how an event is stored (an `iso` date per event), what the filter does to a day (it leaves non-matching events out), and which keys enter and leave a day (Enter focuses its first event, Escape returns to the day).

A day is named for a screen reader by its `aria-label`, which carries the date and the number of events it holds, because a `gridcell` with a label is announced by that name alone. Event titles are placed with `textContent` (the JSX form does the same by escaping), so a title that contains markup is shown as text and never run.

## Example

Drag an event to another day. With the keyboard, move between days with the arrow keys, press Enter to focus the first event of a day, press Space to lift it, use the arrows to reorder it within the day and PageDown or PageUp to move it to the next or previous day, then press Space to drop. Typing in the filter hides the events that do not match.

Pick an authoring pattern below; they all behave the same, and the one you pick is remembered on the other recipes.

<RecipePattern id="element">

The same behavior as a `RadiantElement`. The markup is authored inside the element and the element finds its parts with `@query`; there is nothing to mount, clean up or run again.

<RecipeExample recipe="calendar-events" pattern="element" />

<RecipeCode recipe="calendar-events" pattern="element" />

`createSortableController(this, ...)` and `createRovingController(this, ...)` attach when the element connects and are destroyed when it disconnects, and `@onEvent` listeners follow the same lifecycle. The element keeps its private methods off the names `RadiantElement` owns: a method called `render` would replace the host's own and empty the element. The sortables are created once, one per cell of the grid, which includes the leading and trailing days of the neighbouring months, and share a `SortableGroup` kept in a field. The day cells are built in `onConnected`, after the controllers attached, so the sortables are attached once more there to resolve their containers; a second `attach()` is how a controller finds a target that did not exist yet.

What the Radiant form removes: the `mount` function and its registration, the cleanup that destroys each sortable and the roving controller, and the re-run after a client-side navigation.

</RecipePattern>

<RecipePattern id="component">

The same calendar as one self-contained tag. The element owns its markup: the events and the filter are state, and `render()` draws the filter field, the heading, the weekday headers, the day cells and the events from `buildCalendarMonth` and the other helpers, so the page holds only the tag.

<PrimitiveExample host>
	<calendar-events-app></calendar-events-app>
</PrimitiveExample>

<RecipeCode recipe="calendar-events" pattern="component" />

Moving an event writes a new `events` array and the render draws it; the filter is a second `@state` that `render()` reads, so typing leaves out the events that do not match without any code to hide them. The controllers attach when the element connects, before the first render, so `updated()` attaches them once more when the grid exists, then keeps the roving tab stop in step and focuses the event that moved, found by its id because an event that changed day is a new node. The status line is bound with `this.$.status`, so announcing during a sort patches one text node and does not call `render()` again.

Compared with the Radiant element above, there is no day-building and painting code to keep in step with the state, but the markup lives inside the element, so restyling the structure means editing the class. It also needs the render path on the server to have content before the script runs: this docs build prerenders the tag empty and the client draws it, so the page shows nothing until the script loads, which a page of authored children does not.

</RecipePattern>

<RecipePattern id="controller">

The same behavior as a `RadiantController` attached to markup that already exists. There is no tag to define: the page carries `data-controller="calendar-events"` and the controller finds its parts inside that element.

<RecipeExample recipe="calendar-events" pattern="controller" />

<RecipeCode recipe="calendar-events" pattern="controller" />

The class is the element form's logic on a different base: `@query`, `@onEvent` and the two `create...Controller(this, ...)` calls work unchanged, because a `RadiantController` has the same registration methods as a `RadiantElement`. It has no `onConnected` hook, so the days are built in an override of `connect()` after `super.connect()`, and the sortables are attached once more there to resolve their containers, as in the element form.

Compared with the Radiant element, there is no custom element tag to define, so the markup can come from a server template or a CMS and only has to carry `data-controller`. One registry that the docs site starts over the document attaches the controller to each matching element, including ones inserted later, and disconnects it when the element is removed, which destroys the sortables and the roving controller. The cost is that the script only registers a class: nothing runs until a registry is started, and the controller name is global, where a tag name is already scoped to the page.

</RecipePattern>
