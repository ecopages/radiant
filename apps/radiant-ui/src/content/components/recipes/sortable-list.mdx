# Sortable list

<p class="docs-lede">
	A list whose items the user reorders by dragging or from the keyboard, with each step announced.
</p>

## Goal

A to-do list, a playlist or a priority ranking: the order is data the user edits. The list keeps one tab stop, lifts an item with Space, moves it with the arrow keys and drops it with Space, and a drag with the pointer does the same. A live region says what happened.

## Primitives

- [SortableController](/docs/controllers/sortable) decides where the item lands, by pointer or keyboard, and announces each step. It never moves a node, so the recipe keeps the order itself.
- With `preview: true` the dragged item follows the pointer above the page and a placeholder holds its slot; `createPlaceholder` returns an `li` because the container is a `ul`. The lifted item leaves the example, so its style selects it by `data-sortable-task`, not by an ancestor.
- [reorder](/docs/helpers/ordering) turns the `from` and `to` of a change into the new array, so the order is one array the recipe owns.
- [RovingController](/docs/controllers/roving) gives the list one tab stop and moves it with the arrows. Its `enabled` returns `false` while an item is lifted, so the arrow keys that steer the lifted item do not also move focus.

Left to the recipe: the order array and writing it to the DOM in `onChange`, and refocusing the dropped item.

## Example

Tab into the list, press Space on an item, move it with the arrow keys and press Space to drop it, or drag it with the pointer.

Pick an authoring pattern below; they all behave the same, and the one you pick is remembered on the other recipes.

<RecipePattern id="element">

The same behavior as a `RadiantElement`. The markup is authored inside the element and the element finds its parts with `@query`; there is nothing to mount, clean up or run again.

<RecipeExample recipe="sortable-list" pattern="element" layout="stack" />

<RecipeCode recipe="sortable-list" pattern="element" />

`createSortableController(this, ...)` and `createRovingController(this, ...)` attach when the element connects and are destroyed when it disconnects. They are field initializers because each refers to the other from its callbacks: `enabled` reads the sortable and `onChange` focuses through the roving controller. The items are read in `onConnected`, once the element has its children.

What the Radiant form removes: the `mount` function and its registration, the cleanup that destroys both controllers, and the re-run after a client-side navigation.

</RecipePattern>

<RecipePattern id="component">

The same behavior as a single `RadiantElement` that owns its markup: the tasks are `@state` and `render()` draws the list.

<PrimitiveExample host>
	<sortable-list-app></sortable-list-app>
</PrimitiveExample>

<RecipeCode recipe="sortable-list" pattern="component" />

The tasks are `@state`, so a drop is a new array: `onChange` does not touch the DOM, it writes the reordered tasks with `reorder`, and `render()` moves the keyed items. The sortable and roving controllers are still field initializers that refer to each other, but they read the list through a query instead of a stored `ul` and an `items` array, because the list is drawn by the element. `updated()` runs after each commit: it attaches the sortable to the committed list, syncs the roving tab stop and focuses the item that moved. The status line is bound with `this.$.status`, so announcing during a sort patches one text node and never re-renders the list while an item is lifted.

Compared with the Radiant element above, the markup lives inside the element, so there is nothing to keep in step with the page and the tasks are state you can change, but restyling the structure means editing the class. It also needs the render path on the server to have content before the script runs: this docs build prerenders the tag empty and the client draws it, so the page shows nothing until the script loads, which a page of authored children does not.

</RecipePattern>

<RecipePattern id="controller">

The same behavior as a `RadiantController` attached to markup that is already on the page.

<RecipeExample recipe="sortable-list" pattern="controller" layout="stack" />

<RecipeCode recipe="sortable-list" pattern="controller" />

Compared with the Radiant element, there is no custom element tag to define: the markup is a plain `div` that a server or CMS can render, and `data-controller="sortable-list"` attaches the class through the registry, which the docs site starts once over the document. The body is the element's, with `@query` finding the parts and the sortable and roving controllers declared the same way, because a `RadiantController` accepts `createSortableController(this, ...)` as a host. The items are read in `connect()` after `super.connect()`. When the element is removed the registry disconnects the controller and both primitives are destroyed.

</RecipePattern>

### Styles

The lifted item and the placeholder are styled by `data-sortable-state` and `data-sortable-placeholder`; `touch-action: none` on the items lets a touch drag reorder instead of scrolling. The stylesheet is the `sortable-list.css` tab in the files above.
