# Swipe to dismiss

<p class="docs-lede">
	A card that follows the pointer, dismissed by a horizontal swipe, and with a button that does the same.
</p>

## Goal

A notification, a suggestion or a message in a feed that the user clears with a gesture. A gesture is never the only way: the button is the keyboard and assistive technology path, and both paths end in the same function.

## Primitives

- [PointerDragController](/docs/controllers/pointer-drag) reports the drag, so the card follows the pointer: the recipe writes `--swipe-dx` and `--swipe-opacity` on it and the CSS translates and fades it, with no transition while `data-dragging` is set and a transition on release. Its `canStart` keeps a press on the button from starting a drag.
- [resolveSwipeDirection](/docs/helpers/decisions) decides on release from the drag's `dx`, `dy` and `elapsedMs`: a long drag counts, and so does a short quick flick (`minVelocity`) as long as it is clearly sideways (`dominance`). Past the decision the card flies out and is dismissed; otherwise it springs back.

The recipe uses one `PointerDragController` and the pure decision rather than a second `SwipeController` on the same card: `SwipeController` is built on a `PointerDragController`, so two would listen for the same press twice and finish in an order the recipe does not control. The time comes from the `elapsedMs` of the drag's end.

Left to the recipe: what dismissing does (here it waits for the fly-out animation, hides the card and says so in a live region) and, where the card is hidden while it holds focus, moving focus on to the restore button. A card that only needs the decision and no feedback uses [SwipeController](/docs/controllers/swipe).

## Example

Drag the card sideways at least 48 px, or flick it faster than 0.5 px per ms over at least 16 px, then release. A shorter or slower drag springs back, and so does one that is not at least twice as far sideways as vertically. Or press the Dismiss button. Pick an authoring pattern below; they all behave the same, and the one you pick is remembered on the other recipes.

<RecipePattern id="element">

The same behavior as a `RadiantElement`. The markup is authored inside the element and the element finds its parts with `@query`; there is nothing to mount, clean up or run again.

<RecipeExample recipe="swipe-card" pattern="element" />

<RecipeCode recipe="swipe-card" pattern="element" />

`createPointerDragController(this, ...)` in the constructor attaches the drag when the element connects and destroys it when the element disconnects, and the `@onEvent` listeners for the two buttons follow the same lifecycle. The card, the buttons and the live region are found with `@query`, so the element owns all of them; the pure `resolveSwipeDirection` decision is unchanged.

What the Radiant form removes: the `mount` function and its registration, the cleanup to return and call, and the re-run after a client-side navigation.

</RecipePattern>

<RecipePattern id="component">

The same card as one self-contained tag. The element owns its markup: it keeps whether the card is shown and the status line as state and draws them with `render()`, so there is no markup to author or copy and the page holds only the tag.

<PrimitiveExample host>
	<swipe-card-app></swipe-card-app>
</PrimitiveExample>

<RecipeCode recipe="swipe-card" pattern="component" />

`shown` and `status` are `@state`, so dismissing and restoring write state and `render()` sets `hidden` on the card and the restore button. The drag does not go through state: it writes `--swipe-dx`, `--swipe-opacity` and `data-dragging` straight onto the card, which the render never sets, so a drag does not re-render sixty times a second. Focus moves in `updated()`, after the commit, because the restore button is still hidden when the state changes; the element records where focus should go and `updated()` moves it. The status line is bound with `this.$.status`, so announcing patches one text node.

Compared with the Radiant element above, the markup lives inside the element, so there is nothing to keep in step with the page, but restyling the structure means editing the class. It also needs the render path on the server to have content before the script runs: this docs build prerenders the tag empty and the client draws it, so the page shows nothing until the script loads, which a page of authored children does not.

</RecipePattern>

<RecipePattern id="controller">

The same behavior as a `RadiantController`: a class attached to markup that already exists, found through `data-controller`, with no custom element tag.

<RecipeExample recipe="swipe-card" pattern="controller" />

<RecipeCode recipe="swipe-card" pattern="controller" />

The class body is the element's: `@query` finds the parts, `@onEvent` handles the buttons and `createPointerDragController(this, ...)` attaches the drag on connect and destroys it on cleanup, because a `RadiantController` offers the same two registration methods as a `RadiantElement`. The constructor receives the host element, so it passes it to `super(host)`.

What differs from the Radiant element: there is no tag to define, so the markup can come from a server or a CMS and only needs `data-controller="swipe-card"` on its root. One registry, which this docs site starts over the document, attaches the class to that element, also when it is inserted later, and cleans up when the element is removed.

</RecipePattern>

### Styles

The card follows the drag only through these rules: the recipe writes `--swipe-dx` and `--swipe-opacity` and the stylesheet turns them into a translation and a fade, with no transition while `data-dragging` is set. The stylesheet is the `swipe-card.css` tab in the files above.
