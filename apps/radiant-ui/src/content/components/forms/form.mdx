# Form

## Usage

Wrap fields in `RuiForm` and handle validated values with `onSubmit`. Choose `mode` to control when validation runs.

```tsx
import { RuiForm } from '@ecopages/radiant-ui/form';
import { RuiField } from '@ecopages/radiant-ui/field';
import { RuiLabel } from '@ecopages/radiant-ui/label';
import { RuiInput } from '@ecopages/radiant-ui/input';
import { RuiButton } from '@ecopages/radiant-ui/button';

<RuiForm mode="onSubmit" onSubmit={handleSubmit}>
	<RuiField name="name" rules={{ required: 'Name is required' }}>
		<RuiLabel>Full name</RuiLabel>
		<RuiInput />
	</RuiField>
	<RuiButton type="submit">Create account</RuiButton>
</RuiForm>;
```

## Custom markup

`<rui-form>` coordinates validation across `rui-field` connectors and a composed native form. The `RuiForm` helper stamps `[data-ref="form"]`; it is not required.

```tsx
import '@ecopages/radiant-ui/form';

<rui-form mode="onSubmit">
	<form class="rui-form" data-ref="form" noValidate>
		<rui-field name="name">
			<div class="rui-field">
				<label class="rui-label" data-rui-field-label>
					Name
				</label>
				<input type="text" data-rui-control class="rui-input" />
			</div>
		</rui-field>
		<button type="submit">Submit</button>
	</form>
</rui-form>;
```

Submit buttons outside the native `<form>` are associated via the `form` attribute. Fields register through context — the form does not query control targets directly.

Load `@ecopages/radiant-ui/styles.css` once in your app to style the form and every composed control. When bundling styles per component, import `@ecopages/radiant-ui/form/styles.css` plus the stylesheet for every component used inside the form, such as `field/styles.css`, `textarea/styles.css`, or `number-field/styles.css`.

## Validation timing

<p>
	`onSubmit` validates once on submit and is best for short forms. Use `onBlur` or `onChange` when immediate feedback
	helps data entry.
</p>

## Compose with Radiant controls

<p>
	Every `RuiField` child should be a Radiant control (`RuiInput`, `RuiSelect`, `RuiDateInput`, …). The form store
	discovers values through the Field control protocol; unmarked native inputs are not registered.
</p>

## Native form submission

`RuiForm` always contains a native `<form>`. These are two channels:

- **Store** (`onSubmit` / `rui-submit`): every `RuiField` value
- **Listed controls** (`new FormData(form)` and `action` / `method` navigation): only what the browser lists

`onSubmit` skips native navigation. `action` / `method` without `onSubmit` POSTs listed controls only.

Listed:

- Inner native controls: `RuiInput`, `RuiTextarea`, `RuiCheckbox`, `RuiSwitch`, `RuiRadioGroup`, `RuiCheckboxGroup`
- Form-associated hosts (`name` on the host): `rui-date-input`, `rui-number-field`, `rui-slider`, `rui-knob`. An empty named date submits `''`. A range slider also submits `{name}-max`. Number-field submits the raw number, not the formatted display
- `RuiDateField` is not listed; it copies `name` onto the nested `rui-date-input`
- `RuiDateRangePicker` is not listed; `start-name` / `end-name` land on the nested `rui-date-input` hosts
- `RuiField` copies its `name` onto that control. The field element itself is not listed

Store-only (not in `FormData`): `RuiSelect`, `RuiCombobox`, `RuiListbox`, `RuiTagGroup`.

### Custom form-associated hosts

`RuiField` connects a control to the `RuiForm` store. Native forms use a separate channel: the browser lists a control in `FormData` only when a native form control has a name or a form-associated custom element supplies a value through `ElementInternals`. Register a third-party host before its field connects. Registration supplies store value access and name wiring; it does not make the host form-associated.

```ts
import { customElement, prop } from '@ecopages/radiant';
import { FormAssociatedElement, type FormValue } from '@ecopages/radiant/form-associated-element';
import { registerFieldControl } from '@ecopages/radiant-ui/form';

@customElement('x-tone')
class ToneControl extends FormAssociatedElement {
	@prop({ type: String, reflect: true, defaultValue: '' }) value!: string;

	protected override formValue(): FormValue {
		return this.value;
	}

	protected override restoreFormState(state: FormValue): void {
		this.value = typeof state === 'string' ? state : '';
	}
}

registerFieldControl('x-tone', {
	read: (host) => (host as ToneControl).value,
	write: (host, value) => {
		(host as ToneControl).value = String(value ?? '');
	},
	submission: 'host',
});
```

`FormAssociatedElement` extends `RadiantElement`. Each concrete subclass has its own constructor, so several controls can inherit the base and register under different tags. The base owns the single `ElementInternals`, `name`, `disabled`, effective fieldset disability, submission syncing, and reset. Its inherited static `formAssociated` getter is read when the concrete class is registered. Keep `super.updated(changed)` if you override `updated()`; that call syncs the form value after reactive writes. Likewise, call `super.formDisabledCallback(disabled)` or `super.formResetCallback()` when overriding those browser callbacks.

The first form value sync records the reset state, normally during the first connect update cycle. By default, that state comes from `formValue()`. Override `formState()` when `formValue()` can be `null` for an unnamed host or returns a multi-entry `FormData`; return a value that `restoreFormState()` can read even if the name changes later. For visual disability caused by a parent `<fieldset disabled>`, read `effectiveDisabled` and watch `@onUpdated('effectiveDisabled')`. The catalog hosts support native submission, fieldset disability, and reset. Implement browser state restoration through `formStateRestoreCallback()` when the control needs it.

`RuiForm` also reads the control's own validity, from native `input`, `textarea` and `select` controls (`required`, `type="email"`, `minlength`, `pattern`, `min` and `max`, `step`) and from form-associated hosts. A form-associated host that calls `this.internals?.setValidity(flags, message)` reports the same way. The failing `ValidityState` flag becomes the error `type` (`valueMissing`, `typeMismatch`, `tooShort`, ...), the constraint behind it the `params` (`tooShort`: `{ minLength }`, `tooLong`: `{ maxLength }`, `rangeUnderflow`: `{ min }`, `rangeOverflow`: `{ max }`, `patternMismatch`: `{ pattern }`, `stepMismatch`: `{ step }`, `typeMismatch`: `{ inputType }`; `valueMissing` has none), and the control's `validationMessage` the `message`; no text is invented when a control has none. The built-in store treats it as an input to its validation, with the timing of its own rules, so a native problem blocks submit and shows with `aria-invalid` and `rui-invalid` like any other error, and a rule or resolver message wins over it. An injected store receives it as the `native` fact on the call that carries the value or event. The base exposes `validity` and `validationMessage` on the host; a host that does not extend `FormAssociatedElement` passes a `validity: (host) => ({ valid, type?, message? })` function to `registerFieldControl`. Call `setValidity` before emitting `rui-change`, so change-time validation sees the new state. A custom `resolver` cannot disable the check, a control barred from constraint validation (disabled, for one) reports valid, and a control without validity (or without `ElementInternals`, as on the server) adds no error.

For other hosts, `submission` is `native` by default (name the native ARIA target), or `none` for a store-only control. Set `data-rui-aria-target` on the host when that native input is inside it. A registered host with a declared target binds the field's ARIA state onto it from `fieldContext` (`fieldAria` or `fieldAriaBindings`); see Field.

## Default values

<p>Pass `defaultValues` to pre-populate edit forms. Fields read their initial state from the form store. Multi-value controls (`RuiSelect`, `RuiCombobox`, `RuiListbox`, `RuiCheckboxGroup`, `RuiTagGroup`) store `string[]` — seed them with an array (`{ language: ['ts'] }`). A CSV string still writes because the host parses it; after that the stored value is an array. `RuiSlider` stores `number[]`.</p>

## Inject a form state store

A host that already owns form state, such as a schema-driven forms layer, passes it to the form with the `store` property. The form then becomes a control bridge, and the store owns validation timing, touched and dirty state, defaults and which errors show. Without `store` the form creates its own `FormStore` and behaves as before.

```tsx
<RuiForm store={store}>
	<RuiField name="profile.name">
		<RuiInput />
		<RuiFieldError />
	</RuiField>
</RuiForm>
```

The store implements `FormStateStore`. Paths are the dotted `name` of each `RuiField`, and the store reads and writes a nested tree by them: `profile.name` is `values.profile.name`, and `rows.0.title` is `values.rows[0].title`. The built-in `FormStore` does the same, so `getValues()`, `getSnapshot().values`, `rui-submit` values, `defaultValues`, rules and resolvers all see the nested tree, while the HTML `name` attributes and the keys of `errors`, `touched` and `dirty` stay dotted. An entry in an errors record marks its field invalid even when its `message` is missing or empty, and then shows no text. How an injected store combines errors from different origins is its own decision; the built-in `FormStore` lets an error from `setErrors` replace its own at the same path, clears it when the user edits that field, and borrows no message between them.

| Control event      | The form does                                                                                                                                                                                       |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Value change | `setValue(path, value, { native })`: the value and the control's validity in one call. |
| Blur | `blur(path, { value, native })`, with `value` present only when the user changed the control since the last synchronisation, so a blur is one call. |
| Submit | Writes every control the user changed, then either calls `submitHandler` or awaits `validate(undefined, { native })` with every control's validity and emits `rui-submit` with the snapshot `values` or `rui-invalid` with the snapshot `errors`. |
| Native `reset` | Calls `resetHandler` when it is set, otherwise `reset()`, then rewrites every control from the store, again after the browser's own reset. |
| Store notification | Writes a path's value into its control when that value changed since the form last saw it.                                                                                                          |

Native validity is read from the controls each time and sent as a fact in the same call as the value or event it describes, so a store never holds a fact older than the value it validates. A fact is `{ type, params?, message? }`: the failing `ValidityState` flag (`valueMissing`, `typeMismatch`, `tooShort`, ...), the constraint behind it (`{ minLength: 8 }`, `{ min: 1 }`, `{ max: 10 }`, `{ pattern }`), and the control's own `validationMessage` as a fallback. `null` means the control reports valid, and a call without `native` carries no fact, which a store must not replace with an older one. On `validate` the `native` record is authoritative: it lists every bridged control, `null` for a valid one, and the store drops any fact it held for a path the record omits, so a removed or moved row leaves nothing to release. Only controls marked `data-rui-control`, and Radiant's own controls, are bridged; a bare `<input>` inside a `RuiField` is not read or written. When a store write changes a control's value, the form reports that control's fact on its own with `reportNative(path, native)`, after the notification that wrote it. The store binds the fact to the value it holds, re-validates the path only if it was already validated, whether it passed or failed, or is in a failed scope (so a field that was checked and passed shows an error at once when its control turns invalid, the report never counts as a change, and a reset, which forgets what was validated, is not shown as an error), and ignores a path it does not hold, such as a row that was removed; the form also skips a control that was removed or renamed in the meantime. A fact is an input to the store's validation, not an error to show, so the store decides when it shows, with the same timing as its own rules. The form presents `getSnapshot().errors` as the store gives them, tolerates extra fields on an entry (`source`, `ruleId`, `params`, `all`), and ignores keys with no registered control, such as a form-level `__root__`, which the host renders itself. `validate()` must resolve `false` while the store holds any error at the validated paths, native ones included, and a warning never counts.

The snapshot also carries `warnings`, keyed like `errors`. A warning is advice: it never marks the field invalid, never reaches `aria-invalid`, and never blocks submit. `RuiFieldWarning` is the region that shows it, and `rui-field` fills and hides it the way it does `RuiFieldError`. It renders `role="status"`, a polite live region, and is not part of `aria-describedby`. Set `formatError` to produce the text for errors and warnings, so an issue without a message never shows blank: it receives the store's whole entry, untouched, and `{ path }`. `FormStateStore` is generic over the store's own entry type, so `form.connect(store, { formatError, submitHandler, resetHandler })` holds the store and its handlers together in one binding and infers `issue` and each handler's `store` from the store, so nothing is cast, for example `form.connect(store, { formatError: (issue, { path }) => t(issue.ruleId ?? issue.type, { ...issue.params, path }) })`. Setting `store` and `formatError` as plain properties works for an entry of the minimal `FieldError` shape; an empty result falls back to the issue's `message`.

With an injected store the form ignores `mode`, `revalidate-mode`, field `defaultValue`, `defaultValues`, `defaultValuesData`, `resolver` and field `rules`, because the store owns each of them. A store therefore has no `touched`, `dirty`, `checkValidity()` or submission members to provide, and `rui-field` defaults are never written to it.

The form compares a control with what the control read right after the form last synchronised it, not with the store, so a submit writes only what the user changed: an untouched empty text input reads `''`, and is not written over a store value of `undefined`.

Set `submitHandler` to take over submit. The form writes the changed control values into the store, then calls `submitHandler({ store, validate, readNativeValidity, focus, submitNatively })`: the host counts attempts and submits, `validate(paths?)` is sugar for a host with no submission protocol of its own: it validates through the store with the current validity of every control. A host runtime with a submission token calls its container's `validate` itself with `readNativeValidity()`, which writes the controls the user changed first, so a check outside submit never binds a fact to a value the control does not hold (the form element has the same `readNativeValidity()` method), `focus(path)` moves focus to the interactive element of the control registered for a path, and `submitNatively()` submits the native `<form>` to its `action` and `method`. The form then emits neither `rui-submit` nor `rui-invalid`, and a rejection is reported with `reportError`. Without a handler the form validates and emits as above. Set `resetHandler` to take over the native `reset` event the same way: it is called with `{ store }` instead of `reset()`, may be async, and the form rewrites the controls from the store when it settles and again after the browser's own reset. Both handlers apply only with an injected store.

A store write updates the matching control, and only when that path's value changed: an unrelated store notification leaves input a control holds but has not committed alone. Setting, replacing or clearing `store` re-registers every control: the new store's values are written into the controls, and clearing it returns to the form's own store in the state it left: its earlier values, errors, touched fields and submitted flag, or a fresh store built from `defaultValues` if it never existed. A form that is disconnected holds no subscription to the host store. The built-in store does not rewrite controls after a native `reset`; only the injected path does.

## API

`RuiForm` renders a native `<form>` inside the coordinating `<rui-form>` custom element. The view maps `defaultValues` / `resolver` to `prop:` bindings and keeps authored children inside that native form.

### Attributes

| Attribute             | Type                                                     | Default    | Description                                                     |
| --------------------- | -------------------------------------------------------- | ---------- | --------------------------------------------------------------- |
| `mode`                | `onSubmit` · `onBlur` · `onChange` · `onTouched` · `all` | `onSubmit` | When validation runs.                                           |
| `revalidate-mode`     | `onSubmit` · `onBlur` · `onChange` · `onTouched` · `all` | `onChange` | When fields re-validate after a failed submit.                  |
| `data-default-values` | `string`                                                 |            | JSON-serialized default values for SSR / JSX attribute channel. |
| `action`              | `string`                                                 |            | Native form destination when `onSubmit` is not provided.        |
| `method`              | `string`                                                 |            | Native form HTTP method when `onSubmit` is not provided.        |

### Props

| Prop            | Type                                   | Description                                                                                                                    |
| --------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `defaultValues` | `Partial<FieldValues>`                 | Initial values; fields read their state from the form store.                                                                   |
| `resolver`      | `Resolver<T>`                          | Custom validation resolver (e.g. from `createRulesResolver`).                                                                  |
| `submitHandler` | `(context: { store, validate, readNativeValidity, focus, submitNatively }) => void \| Promise<void>` | With an injected store, takes over submit after the form writes changed control values. |
| `resetHandler` | `(context: { store }) => void \| Promise<void>` | With an injected store, takes over the native `reset` event. |
| `formatError` | `(issue, { path }) => string` | Text for errors and warnings; an empty result falls back to `message`. |
| `store`         | `FormStateStore`                       | A host-owned form state store that owns validation timing, field state, defaults and errors; see Inject a form state store.    |
| `onSubmit`      | `(values: T) => void \| Promise<void>` | Receives the store. Skips native navigation. When omitted, `action` or `method` POSTs listed controls after validation passes. |

### Light-DOM contract

| Target                               | Required               | Host writes                     | Author owns                                   |
| ------------------------------------ | ---------------------- | ------------------------------- | --------------------------------------------- |
| `[data-ref="form"]`                  | yes                    | `id` when wiring orphan submits | native `<form noValidate>` and field children |
| `button[type="submit"]` outside form | no                     | `form` attribute                | submit buttons on the host                    |
| `rui-field` descendants              | yes (for registration) | —                               | each field's control tree                     |

Nested hosts: `rui-field` and each field's control host.

### Context

`formContext` exposes `ready`, `revision`, `fields`, `errors`, `actions`, and the live `store` once the form is ready (the injected `FormStateStore`, or the form's own `FormStore`). Scoped consumers resolve the nearest provider (`@consumeContext` / `ContextSubscriptionRequestEvent`) and use `context.store` for `getValue` / `setValue`, `reset`, `subscribe`, and `validate`; narrow with `instanceof FormStore` for the rest of `FormStore`. Nested forms still resolve the nearest provider. Without a `submitHandler`, every submission ends in `rui-submit` or `rui-invalid`. With the built-in store, `FormStore.isSubmitting` stays true until the submission settles, including an awaited `onSubmit`, and is always cleared. A validator that throws ends the submission with `rui-invalid` and `detail.error` set. A rejection from `onSubmit` clears `isSubmitting` and is reported with `reportError`, so `window` sees an `error` event and there is no unhandled rejection. An injected store has no submission state of its own in the form; the driver applies the same two outcomes. A `RuiField` registers once and keeps that registration while its `name` is unchanged. `actions.register` returns a handle, `{ rename(name), unregister() }`, that identifies the registration rather than its name. Changing `name` calls `handle.rename`, which moves the field's value, errors, touched and dirty state to the new name with one notification and no moment where the value is missing, and two keyed rows can swap names in two calls without either registration being lost. With an injected store a rename never writes a value: the control is rebound to the new path and seeded from the store there, even when the store holds nothing, and deleting the old path is the host's decision. A form that is disconnected withdraws the native errors it sent to an injected store. Hydration payloads contain presentation only (`ready`, `revision`, `fields`, `errors`); they never include the store or its actions. `RuiField` reads the matching field state and applies it to its control as `aria-invalid`; use `fieldContext` for a control's local `error` and `invalid` values.

| Event         | Detail                                                              | Description                                                                                                                                   |

| `rui-submit`  | `{ values: T }`                                                     | Emitted when validation passes.                                                                                                               |

## Accessibility

- Submit buttons should use `type="submit"` inside the form for keyboard submission.
- Announce form-level errors at the top when multiple fields fail validation.
- Focus the first invalid field after a failed submit attempt.
