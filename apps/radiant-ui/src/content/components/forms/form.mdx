## Usage

Wrap fields in `RuiForm` and handle validated values with `onSubmit`. Choose `mode` to control when validation runs.

```tsx
import { RuiForm } from '@ecopages/radiant-ui/form';
import { RuiField } from '@ecopages/radiant-ui/field';
import { RuiLabel } from '@ecopages/radiant-ui/label';
import { RuiInput } from '@ecopages/radiant-ui/input';
import { RuiButton } from '@ecopages/radiant-ui/button';

<RuiForm mode="onSubmit" onSubmit={handleSubmit}>
	<RuiField name="name" rules={{ required: 'Name is required' }}>
		<RuiLabel>Full name</RuiLabel>
		<RuiInput />
	</RuiField>
	<RuiButton type="submit">Create account</RuiButton>
</RuiForm>;
```

## Custom markup

`<rui-form>` coordinates validation across `rui-field` connectors and a composed native form. The `RuiForm` helper stamps `[data-ref="form"]`; it is not required.

```tsx
import '@ecopages/radiant-ui/form';

<rui-form mode="onSubmit">
	<form class="rui-form" data-ref="form" noValidate>
		<rui-field name="name">
			<div class="rui-field">
				<label class="rui-label" data-rui-field-label>
					Name
				</label>
				<input type="text" data-rui-control class="rui-input" />
			</div>
		</rui-field>
		<button type="submit">Submit</button>
	</form>
</rui-form>;
```

Submit buttons outside the native `<form>` are associated via the `form` attribute. Fields register through context — the form does not query control targets directly.

Load `@ecopages/radiant-ui/styles.css` once in your app to style the form and every composed control. When bundling styles per component, import `@ecopages/radiant-ui/form/styles.css` plus the stylesheet for every component used inside the form, such as `field/styles.css`, `textarea/styles.css`, or `number-field/styles.css`.

## Validation timing

<p>
	`onSubmit` validates once on submit and is best for short forms. Use `onBlur` or `onChange` when immediate feedback
	helps data entry.
</p>

## Compose with Radiant controls

<p>
	Every `RuiField` child should be a Radiant control (`RuiInput`, `RuiSelect`, `RuiDateInput`, …). The form store
	discovers values through the Field control protocol; unmarked native inputs are not registered.
</p>

## Native form submission

`RuiForm` always contains a native `<form>`. These are two channels:

- **Store** (`onSubmit` / `rui-submit`): every `RuiField` value
- **Listed controls** (`new FormData(form)` and `action` / `method` navigation): only what the browser lists

`onSubmit` skips native navigation. `action` / `method` without `onSubmit` POSTs listed controls only.

Listed:

- Inner native controls: `RuiInput`, `RuiTextarea`, `RuiCheckbox`, `RuiSwitch`, `RuiRadioGroup`, `RuiCheckboxGroup`
- Form-associated hosts (`name` on the host): `rui-date-input`, `rui-number-field`, `rui-slider`, `rui-knob`. An empty named date submits `''`. A range slider also submits `{name}-max`. Number-field submits the raw number, not the formatted display
- `RuiDateField` is not listed; it copies `name` onto the nested `rui-date-input`
- `RuiDateRangePicker` is not listed; `start-name` / `end-name` land on the nested `rui-date-input` hosts
- `RuiField` copies its `name` onto that control. The field element itself is not listed

Store-only (not in `FormData`): `RuiSelect`, `RuiCombobox`, `RuiListbox`, `RuiTagGroup`.

### Custom form-associated hosts

`RuiField` connects a control to the `RuiForm` store. Native forms use a separate channel: the browser lists a control in `FormData` only when a native form control has a name or a form-associated custom element supplies a value through `ElementInternals`. Register a third-party host before its field connects. Registration supplies store value access and name wiring; it does not make the host form-associated.

```ts
import { customElement, prop } from '@ecopages/radiant';
import { FormAssociatedElement, type FormValue } from '@ecopages/radiant/form-associated-element';
import { announceControlConnect, registerFieldControl } from '@ecopages/radiant-ui/form';

@customElement('x-tone')
class ToneControl extends FormAssociatedElement {
	@prop({ type: String, reflect: true, defaultValue: '' }) value!: string;

	protected override onConnected(): void {
		announceControlConnect(this);
	}

	/** Commit a choice, then dispatch `input` and `change` on the host so the field writes the new value. */
	choose(value: string): void {
		this.value = value;
		this.dispatchEvent(new InputEvent('input', { bubbles: true, composed: true }));
		this.dispatchEvent(new Event('change', { bubbles: true }));
	}

	protected override formValue(): FormValue {
		return this.value;
	}

	protected override restoreFormState(state: FormValue): void {
		this.value = typeof state === 'string' ? state : '';
	}
}

registerFieldControl('x-tone', {
	read: (host) => (host as ToneControl).value,
	write: (host, value) => {
		(host as ToneControl).value = String(value ?? '');
	},
	submission: 'host',
});
```

A field writes a native control (`<input>`, `<textarea>`, `<select>`) on its native `input` and `change` events. It writes any other control, including a host like this one, on the same two events, but only when the event target is the control host (or a member native input of a wrapper or group), because a nested part's events also reach the field. A wrapper or group whose own native inputs dispatch the events, as `rui-checkbox` does, registers with `events: 'members'` in the adapter (`FieldControlAdapter.events: 'host' | 'members'`, `'host'` by default). A custom host must therefore dispatch `input` (and `change` on commit) on itself after it updates `value`, with no `detail`, and announce itself with `announceControlConnect(this)` (a bubbling, composed `rui-control-connect` event) when it connects, so a field that registered before the control existed seeds it from the form's value and reads its validity. Every Radiant control host does. A native `<input>`, `<select>` or `<textarea>` marked `data-rui-control` announces nothing: it must already be inside its field when the field connects, and one inserted later is picked up on the field's next sync (a store notification or a re-render).

`FormAssociatedElement` extends `RadiantElement`. Each concrete subclass has its own constructor, so several controls can inherit the base and register under different tags. The base owns the single `ElementInternals`, `name`, `disabled`, effective fieldset disability, submission syncing, reset, and restore after back/forward or autofill (`formStateRestoreCallback` writes the saved state back with `restoreFormState()`). Its inherited static `formAssociated` getter is read when the concrete class is registered. Keep `super.updated(changed)` if you override `updated()`; that call syncs the form value after reactive writes. Likewise, call `super.formDisabledCallback(disabled)`, `super.formResetCallback()` or `super.formStateRestoreCallback(state, mode)` when overriding those browser callbacks. In `autocomplete` mode the browser passes the autofilled string, not a saved state; override the callback when your `formState()` is not parseable from the submission string, as `RuiSlider` does for a range.

The first form value sync records the reset state, normally during the first connect update cycle. By default, that state comes from `formValue()`. Override `formState()` when `formValue()` can be `null` for an unnamed host or returns a multi-entry `FormData`; return a value that `restoreFormState()` can read even if the name changes later. For visual disability caused by a parent `<fieldset disabled>`, read `effectiveDisabled` and watch `@onUpdated('effectiveDisabled')`. The catalog hosts support native submission, fieldset disability, and reset. Implement browser state restoration through `formStateRestoreCallback()` when the control needs it.

The control's own validity is read as described in [Native validity](#native-validity).

For other hosts, `submission` is `native` by default (name the native ARIA target), or `none` for a store-only control. Set `data-rui-aria-target` on the host when that native input is inside it. A registered host with a declared target binds the field's ARIA state onto it from `fieldContext` (`fieldAria` or `fieldAriaBindings`); see Field.

## Default values

<p>Pass `defaultValues` to pre-populate edit forms. Fields read their initial state from the form store. Multi-value controls (`RuiSelect`, `RuiCombobox`, `RuiListbox`, `RuiCheckboxGroup`, `RuiTagGroup`) store `string[]` — seed them with an array (`{ language: ['ts'] }`). A CSV string still writes because the host parses it; after that the stored value is an array. `RuiSlider` stores `number[]`.</p>

## Native validity

Native validity is evidence, not configuration. The browser computes `element.validity` from the element's attributes and its value, and `rui-form` reads it and forwards the result: the failing `ValidityState` flag as the error `type`, the constraint behind it as `params`, and the control's own `validationMessage` as a fallback `message`. Nobody edits a native verdict and there is no switch for it; a control with no constraint attributes contributes nothing.

Sources: native `input`, `textarea` and `select` controls (`required`, `type="email"`, `minlength`, `maxlength`, `min`, `max`, `step`, `pattern`), and form-associated hosts. A form-associated host that calls `this.internals?.setValidity(flags, message)` reports the same way, and a host that does not extend `FormAssociatedElement` passes a `validity: (host) => ({ valid, type?, params?, message? })` function to `registerFieldControl`. Call `setValidity` before dispatching `input`, so change-time validation sees the new state. A control barred from constraint validation (disabled, for one) reports valid, and a control without validity (or without `ElementInternals`, as on the server) contributes nothing. Only controls marked `data-rui-control`, and Radiant's own controls, are bridged; a bare `<input>` inside a `RuiField` is neither read nor written.

| Flag | `params` | Constraint attribute |
| --- | --- | --- |
| `valueMissing` | none | `required` |
| `typeMismatch` | `{ inputType }` | `type="email"`, `type="url"` |
| `patternMismatch` | `{ pattern }` | `pattern` |
| `tooShort` | `{ minLength }` | `minlength` (only after the user edits the value) |
| `tooLong` | `{ maxLength }` | `maxlength` |
| `rangeUnderflow` | `{ min }` | `min` (a number for `type="number"` and `"range"`) |
| `rangeOverflow` | `{ max }` | `max` |
| `stepMismatch` | `{ step }` | `step` |
| `badInput`, `customError` | none | the browser, or `setValidity` |

With the built-in store a native problem is an input to its validation, with the timing of its own rules: it blocks submit and shows with `aria-invalid` and `rui-invalid` like any other error, and a rule or resolver message replaces its text but still blocks. A `resolver` cannot disable it; remove the attribute instead. With an injected store, the store decides when it shows, with the same timing as its own rules; see [Inject a form state store](#inject-a-form-state-store).

`rui-form` renders `<form noValidate>`, so the browser's own validation bubbles never appear, while `:invalid` CSS and native submission keep working.

## Inject a form state store

A host that already owns form state, such as a schema-driven forms layer, hands it to the form with `form.connect(store, handlers)`, the only way to inject a store. The form then becomes a control bridge, and the store owns validation timing, touched and dirty state, defaults and which errors and warnings show. Without `connect` the form creates its own `FormStore`. For a minimal store from scratch, see [Write a form state store](/docs/getting-started/write-a-form-state-store).

<Canvas of={Injected} meta={injectedMeta} />

```tsx
<RuiForm ref={(form) => (form ? form.connect(store, { formatError, submitHandler, resetHandler }) : undefined)}>
	<RuiField name="profile.name">
		<RuiInput />
		<RuiFieldError />
	</RuiField>
</RuiForm>
```

`connect` returns a disposer, and a `ref` callback may return it as its cleanup, or keep it: `const disconnect = form.connect(store, { formatError, submitHandler, resetHandler })`. Calling `connect` again with the same store replaces only the handlers; with another store it also re-registers every control and writes the new store's values into them. The disposer returns the form to its own store in the state it left: its earlier values, errors, touched fields and submitted flag, or a fresh store built from `defaultValues` if it never had one. It does nothing once another `connect` replaced its binding. The `formatError` property applies to the form's own store only, and a form that is disconnected from the document holds no subscription to the host store.

The store implements `FormStateStore`. Paths are the dotted `name` of each `RuiField`, and the store reads and writes a nested tree by them: `profile.name` is `values.profile.name`, and `rows.0.title` is `values.rows[0].title`. The built-in `FormStore` does the same, so `getValues()`, `getSnapshot().values`, `rui-submit` values, `defaultValues`, rules and resolvers all see the nested tree, while the HTML `name` attributes and the keys of `errors`, `touched` and `dirty` stay dotted. An entry in an errors record marks its field invalid even when its `message` is missing or empty. How an injected store combines errors from different origins is its own decision; the built-in `FormStore` lets an error from `setErrors(source, errors)` replace its own at the same path, clears it when the user edits that field, and borrows no message between them. `FormStore.errors` is read-only and returns the merged errors: add a source's errors with `setErrors`, replace them by calling it again with the same `source`, and remove them with `setErrors(source, {})` or `clearErrors(path?)`.

| Control event | The form does |
| --- | --- |
| Value change | `setValue(path, value)`, then `reportNative({ [path]: fact })` straight away. |
| Blur | Writes and reports the control first if the user changed it since the last synchronisation, then `blur(path)`. |
| Submit | Calls `sync()`, then either calls `submitHandler` or awaits `validate()` and emits `rui-submit` with the snapshot `values` or `rui-invalid` with the snapshot `errors`. A `validate()` that resolves `false` while the snapshot holds no error, such as a check a newer write overtook, ends the submission with neither event. |
| Native `reset` | Calls `resetHandler` when it is set, otherwise `reset()`, then rewrites every control from the store, again after the browser's own reset, and reports every control's fact again. |
| Store notification | Writes a path's value into its control when that value changed since the form last saw it, and reports the control's fact after the notification. |
| Seed, rename, connect | A control is seeded from the store when it registers or connects (`rui-control-connect`), and a rename (a row that moved) rebinds the control to its new path and seeds it from the store there; it never writes a value. Each reports the control's fact after the change, and a rename withdraws the old path. |
| Disconnect | Reports `null` for the control's path, unless another live control is bound to that path when the report runs, as when rows move. |

Native validity is pushed, never pulled. A fact is `{ type, params?, message? }`; see [Native validity](#native-validity) for what each flag carries. `reportNative(facts)` maps each path to its fact, or to `null` when the control reports valid or left the form. The form calls it whenever a control's value or presence changes, from either side and after the change settles: synchronously right after `setValue` for a user change, so a store holds the fact for a value before it handles `blur`, and through a microtask for everything else, with one call carrying every fact queued meanwhile. The store binds each fact to the value it holds, re-validates a path only if it was already validated, whether it passed or failed, or is in a failed scope (so a field that was checked and passed shows an error at once when its control turns invalid, a report never counts as a change, and a reset, which forgets what was validated, is not shown as an error), keeps the fact until the path is reported again, and ignores a non-`null` fact for a path it does not hold, such as a row that was removed. The form skips a control that was removed or renamed in the meantime, and a report the store rejects goes to `reportError`.

`sync()` writes every control the user changed into the store and reports every bridged control's fact. `rui-form` calls it before `submitHandler` and before its own `validate`, and a host that validates the store itself outside submit calls it first.

A fact is an input to the store's validation, not an error to show, so the store decides when it shows. The form presents `getSnapshot().errors` as the store gives them, tolerates extra fields on an entry (`source`, `ruleId`, `params`, `all`), and ignores keys with no registered control, such as a form-level `__root__`, which the host renders itself. `validate()` must resolve `false` while the store holds any error at the validated paths, native ones included, and a warning never counts.

The snapshot also carries `warnings`, keyed like `errors`. A warning is advice: it never marks the field invalid, never reaches `aria-invalid`, and never blocks submit. `RuiFieldWarning` is the region that shows it, and `rui-field` fills and hides it the way it does `RuiFieldError`. It renders `role="status"`, a polite live region, and is not part of `aria-describedby`. Pass `formatError` to `connect` to produce the text for errors and warnings, so an issue without a message never shows blank: it receives the store's whole entry, untouched, and `{ path }`, and an empty result falls back to the issue's `message`. `FormStateStore` is generic over the store's own entry type, so `connect` infers `issue` and each handler's `store` from the store and nothing is cast, for example `form.connect(store, { formatError: (issue, { path }) => t(issue.ruleId ?? issue.type, { ...issue.params, path }) })`.

With an injected store the form ignores `mode`, `revalidate-mode`, field `defaultValue`, `defaultValues`, `defaultValuesData`, `resolver` and field `rules`, because the store owns each of them. A store therefore has no `touched`, `dirty`, `checkValidity()` or submission members to provide, and `rui-field` defaults are never written to it. The form compares a control with what the control read right after the form last synchronised it, not with the store, so a submit writes only what the user changed: an untouched empty text input reads `''`, and is not written over a store value of `undefined`.

Pass `submitHandler` to `connect` to take over submit. The form calls `sync()`, then calls it with a context:

| Member | What it does |
| --- | --- |
| `submitNatively()` | Submits the native `<form>` to its `action` and `method`. |

The host holds its own store, so the context carries no `store`: validate it, count attempts and move focus with `form.focusField(paths)`. The form then emits neither `rui-submit` nor `rui-invalid`, and a rejection is reported with `reportError`. The handler owns submission, so the form does not gate it: every submit calls the handler, even while an earlier call is pending, and the handler decides what a second submit means, such as ignoring it while busy. Without a handler the form validates and emits as above. Pass `resetHandler` to take over the native `reset` event the same way: it is called with no argument instead of `reset()`, may be async, and the form rewrites the controls from the store when it settles and again after the browser's own reset. Both handlers apply only with an injected store. The built-in store does not rewrite controls after a native `reset`; only the injected path does.

## API

`RuiForm` renders a native `<form>` inside the coordinating `<rui-form>` custom element. The view maps `defaultValues`, `resolver` and `formatError` to `prop:` bindings and keeps authored children inside that native form.

### Attributes

| Attribute             | Type                                                     | Default    | Description                                                     |
| --------------------- | -------------------------------------------------------- | ---------- | --------------------------------------------------------------- |
| `mode`                | `onSubmit` · `onBlur` · `onChange` · `onTouched` · `all` | `onSubmit` | When validation runs.                                           |
| `revalidate-mode`     | `onSubmit` · `onBlur` · `onChange` · `onTouched` · `all` | `onChange` | When fields re-validate after a failed submit.                  |
| `data-default-values` | `string`                                                 |            | JSON-serialized default values for SSR / JSX attribute channel. |
| `action`              | `string`                                                 |            | Native form destination when `onSubmit` is not provided.        |
| `method`              | `string`                                                 |            | Native form HTTP method when `onSubmit` is not provided.        |

### Props

| Prop            | Type                                   | Description                                                                                                                    |
| --------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `defaultValues` | `Partial<FieldValues>`                 | Initial values; fields read their state from the form store.                                                                   |
| `resolver`      | `Resolver<T>`                          | Custom validation resolver (e.g. from `createRulesResolver`).                                                                  |
| `formatError` | `(issue, { path }) => string` | Text for the errors and warnings of the form's own store; an empty result falls back to `message`. A connected store takes its formatter from `connect`. |
| `onSubmit`      | `(values: T) => void \| Promise<void>` | Receives the store. Skips native navigation. When omitted, `action` or `method` POSTs listed controls after validation passes. |

### Light-DOM contract

| Target                               | Required               | Host writes                     | Author owns                                   |
| ------------------------------------ | ---------------------- | ------------------------------- | --------------------------------------------- |
| `[data-ref="form"]`                  | yes                    | `id` when wiring orphan submits | native `<form noValidate>` and field children |
| `button[type="submit"]` outside form | no                     | `form` attribute                | submit buttons on the host                    |
| `rui-field` descendants              | yes (for registration) | —                               | each field's control tree                     |

Nested hosts: `rui-field` and each field's control host.

### Context

`formContext` exposes `ready`, `revision`, `fields`, `errors`, `actions`, and the live `store` once the form is ready (the injected `FormStateStore`, or the form's own `FormStore`). Scoped consumers resolve the nearest provider (`@consumeContext` / `ContextSubscriptionRequestEvent`) and use `context.store` for `getValue` / `setValue`, `reset`, `subscribe`, and `validate`; narrow with `instanceof FormStore` for the rest of `FormStore`. Nested forms still resolve the nearest provider. Without a `submitHandler`, every submission ends in `rui-submit` or `rui-invalid`, and the form runs one submission at a time: a submit while one is pending, through validation and an awaited `onSubmit`, is ignored, with no second validation and no event. A submission whose store was replaced by `connect`, or removed by its disposer, before validation settled ends without `rui-submit`, `rui-invalid` or `onSubmit`. A new submit is accepted once the pending one settles, even when it threw. With the built-in store, `FormStore.isSubmitting` stays true until the submission settles, including an awaited `onSubmit`, and is always cleared. A validator that throws ends the submission with `rui-invalid` and `detail.error` set. A rejection from `onSubmit` clears `isSubmitting` and is reported with `reportError`, so `window` sees an `error` event and there is no unhandled rejection. An injected store has no submission state of its own in the form; the driver applies the same two outcomes. A `RuiField` registers once and keeps that registration while its `name` is unchanged. `actions.register` returns a handle, `{ rename(name), unregister(), refresh() }`, that identifies the registration rather than its name. Changing `name` calls `handle.rename`, which moves the field's value, errors, touched and dirty state to the new name with one notification and no moment where the value is missing, and two keyed rows can swap names in two calls without either registration being lost. With an injected store a rename never writes a value: the control is rebound to the new path and seeded from the store there, even when the store holds nothing, and deleting the old path is the host's decision. Hydration payloads contain presentation only (`ready`, `revision`, `fields`, `errors`); they never include the store or its actions. `RuiField` reads the matching field state and applies it to its control as `aria-invalid`; use `fieldContext` for a control's local `error` and `invalid` values.

### Methods

| Method | Description |
| --- | --- |
| `connect(store, handlers?)` | Injects a `FormStateStore` with its `formatError`, `submitHandler` and `resetHandler`, typed by the store's own issue type. Returns a disposer. |
| `focusField(paths)` | Focuses the first registered field among `paths` in document order, with the built-in or an injected store. Unknown paths are ignored, and nothing happens when none has a field. Use it to move focus outside a submit, such as after a failed step. |
| `sync()` | Writes the controls the user changed into the injected store and reports every bridged control's fact. Submit calls it first. |

### Events

| Event         | Detail                                                              | Description                                                                                                                                   |
| ------------- | ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `rui-submit`  | `{ values: T }`                                                     | Emitted when validation passes.                                                                                                               |
| `rui-invalid` | `{ errors: Partial<Record<string, FieldError>>; error?: unknown }` | Emitted when validation fails on submit. `error` is set when a validator threw instead of reporting errors: the submission counts as invalid. |

These are the form's own events. The controls inside it dispatch the platform's `input` and `change`; `rui-change` remains only for non-form components (tabs, tree, menus, table, calendar, cycle-toggle).

## Accessibility

- Submit buttons should use `type="submit"` inside the form for keyboard submission.
- Announce form-level errors at the top when multiple fields fail validation.
- Focus the first invalid field after a failed submit attempt.
