# RadiantComponent
---

`RadiantComponent` is the JSX-first base class in Radiant.

It extends `RadiantElement` and adds the host render loop that connects `render()` to the `@ecopages/jsx` DOM and SSR renderers.

It is additive in the type hierarchy, but it is not meant to make `RadiantElement` obsolete. The important docs distinction is host ownership: choose `RadiantComponent` when the host itself should own a JSX view.

Use it when the custom element itself should:

- describe its host view with JSX
- rerender from tracked reactive reads during `render()`
- hydrate SSR output in place
- project authored light-DOM content through literal `<slot>` tags
- expose reactive JSX bindings by default for `@prop`, `@state`, `createReactiveProp(...)`, and `createReactiveField(...)`

If you do not override `render()`, the base implementation behaves like `<slot />`, so direct host children become the default unnamed slot content.

## Example

```tsx
/** @jsxImportSource @ecopages/jsx */

import { RadiantComponent, customElement, prop, state } from '@ecopages/radiant';

type CounterCardBindings = {
	count: number;
	label: string;
};

@customElement('counter-card')
export class CounterCard extends RadiantComponent<CounterCardBindings> {
	@prop({ type: Number, reflect: true, defaultValue: 0 }) count!: number;
	@state label = 'Counter';

	private increment = () => {
		this.count += 1;
	};

	override render() {
		return (
			<section>
				<h2>{this.label}</h2>
				<p>Count: {this.count}</p>
				<button type="button" on:click={this.increment}>
					Increment
				</button>
			</section>
		);
	}
}
```

## Typing Public Props vs Internal Bindings

The generic on `RadiantComponent<Bindings>` describes the component's internal
bindable surface, not the public JSX attribute contract by default.

Use a separate public props type when consumers should only see a subset of the
reactive members exposed inside the component.

- Public props: what `<my-element ... />` may pass.
- Bindings: what `this.$.key`, `this.bindings.key`, and `this.bind('key')` may read.

See [Best Practices](/docs/getting-started/best-practices) for the canonical
`Props` plus `Bindings` pattern.

## How It Works Behind The Scenes

`RadiantComponent` adds four key behaviors on top of `RadiantElement`.

### 1. First Connect Is Deferred To A Microtask

On `connectedCallback()`, the component waits one microtask before the first render.

That gives decorators, inherited setup, and context wiring a chance to finish before the initial JSX pass runs.

### 2. Hydration And Client Render Share The Same `render()` Output

On first connect, Radiant checks whether the host already contains hydration markers.

- If markers exist, it calls `hydrate()` and reconnects listeners and property bindings onto the SSR DOM.
- If markers do not exist, it calls `update()` and mounts fresh client DOM.

In both cases the source of truth is still `render()`.

### 3. Render Reads Are Tracked

Plain reads of `@prop`, `@state`, and `@signal` members during `render()` participate in tracked invalidation.

That means `this.count` and `this.label` can rerender the host without extra `@onUpdated(...)` wiring when they are part of the rendered output.

### 4. `update()` And `requestUpdate()` Still Matter

`render()` still only describes the view. It does not mutate the DOM by itself.

`update()` runs the DOM renderer against the host element, and `requestUpdate()` schedules a coalesced rerender. Use them when state changes happen outside tracked render reads or when a decorator such as `@contextSelector(...)` needs to refresh the host after imperative work.

### 5. Reactive JSX Bindings Default To On

`RadiantComponent` overrides the host binding policy inherited from `RadiantElement`.

That means when you omit `bind`, these APIs opt into JSX bindings automatically:

- `@prop(...)`
- `@state`
- `createReactiveProp(...)`
- `createReactiveField(...)`

So `this.$.count`, `this.bindings.count`, and `this.bind('count')` are available by default for component-style hosts.

## SSR Helpers

`RadiantComponent` also exposes SSR helpers:

- `renderToString(...)` serializes only the current view returned by `render()`.
- `renderHostToString(...)` serializes the custom-element host plus the current view.
- `renderHost()` returns the same host output as a JSX renderable.

Use those methods when you need the host element and view to stay aligned across server and client rendering.

## Slots And Light-DOM Projection

`RadiantComponent` supports literal `<slot>` tags in `render()` even though the component renders in the light DOM.

- Omit `name` for the default slot.
- Use `name="..."` for named slots.
- Put fallback JSX inside the `<slot>` tag.
- Assign authored host children with the standard `slot` attribute.

```tsx
/** @jsxImportSource @ecopages/jsx */

import { RadiantComponent, customElement } from '@ecopages/radiant';

@customElement('marketing-card')
export class MarketingCard extends RadiantComponent {
	override render() {
		return (
			<article class="card">
				<slot name="heading">
					<h2>Fallback heading</h2>
				</slot>
				<div class="card-body">
					<slot>
						<p>Fallback body copy</p>
					</slot>
				</div>
			</article>
		);
	}
}
```

```tsx
<marketing-card>
	<h2 slot="heading">Projected heading</h2>
	<p>Projected body copy</p>
</marketing-card>
```

This behaves like a Radiant-managed content projection model, not native shadow-DOM slot distribution. See [Slots](/docs/components/slots) and [@querySlot](/docs/decorators/query-slot).

## Relationship To RadiantElement

`RadiantComponent` is not a replacement for `RadiantElement`. It is the JSX-host layer built on top of it.

If you think of it as a superset, be careful about what that means. It inherits from `RadiantElement`, but the practical choice is still about what owns the host DOM.

- `RadiantElement` is still the base for lower-level custom elements.
- `RadiantElement` does not need SSR to be useful. It works perfectly well as a client-only reactive custom element.
- `RadiantElement` custom elements can still be rendered inside JSX trees.
- `RadiantComponent` is what you extend when the host itself should own a JSX view, hydrate SSR output, or project authored slot content.

Use `RadiantComponent` because the host should render, not because `RadiantElement` is somehow incomplete.

See [RadiantElement](/docs/components/radiant-element) and [Todo App](/docs/examples/todo-app).
