# @consumeContext

Use `@consumeContext(...)` to inject the nearest matching context provider onto a field.

It works on both `RadiantElement` and `RadiantController` hosts.

## Example

```typescript
import { RadiantElement, customElement } from '@ecopages/radiant';
import { consumeContext, type ContextProvider } from '@ecopages/radiant/context';

import { themeContext } from './theme-provider';

@customElement('theme-label')
export class ThemeLabel extends RadiantElement {
	@consumeContext(themeContext)
	provider!: ContextProvider<typeof themeContext>;

	override connectedCallback() {
		super.connectedCallback();
		this.textContent = `Theme: ${this.provider.getContext().mode}`;
	}
}
```

The injected field gives you access to the provider API, including `getContext()` and `setContext(...)`.

The field is `undefined` until a matching provider answers. The consumer asks once more in a microtask, so a provider that upgrades right after it still answers; a host with no provider by then keeps `undefined`. Declare the field optional (`provider?: ContextProvider<typeof themeContext>`) when a provider can be missing; the `!` form above fits a host that is always rendered inside one. See [Typing Decorated Fields](/docs/decorators#typing-decorated-fields).

On controllers, this is often the simplest way to read and write shared state imperatively from event handlers or `render()`.

## When To Use It

- Use `@consumeContext(...)` when the host needs the provider object to call `getContext()` or `setContext(...)`.
- Use [@contextSelector](/docs/context/context-selector) when the host should bind a field to the current context value and rerender automatically.
- Use [@onContextUpdate](/docs/context/on-context-update) when a context change should trigger imperative side effects.

## RadiantController Example

```typescript
import { RadiantController } from '@ecopages/radiant';
import { consumeContext, type ContextProvider } from '@ecopages/radiant/context';

import { themeContext } from './theme-provider';

export class ThemePanelController extends RadiantController {
	@consumeContext(themeContext)
	provider!: ContextProvider<typeof themeContext>;

	override render() {
		return <p>Theme: {this.provider.getContext().mode}</p>;
	}
}
```

## Client And SSR Behavior

- During SSR the field can resolve from the active SSR context stack.
- On the client it falls back to the DOM event-based context channel.

## Multiple Contexts

One host can consume multiple contexts by applying the decorator to multiple fields.

```typescript
@consumeContext(themeContext) theme!: ContextProvider<typeof themeContext>;
@consumeContext(authContext) auth!: ContextProvider<typeof authContext>;
```

## Manual Alternative

If you need lower-level control, you can dispatch a context request event directly. `ContextRequestEvent` is the `context-request` event of the [community context protocol](https://github.com/webcomponents-cg/community-protocols/blob/main/proposals/context.md): the callback receives the context value, not the provider.

```typescript
import { RadiantElement, customElement } from '@ecopages/radiant';
import { ContextRequestEvent } from '@ecopages/radiant/context';

import { themeContext } from './theme-provider';

@customElement('theme-label')
export class ThemeLabel extends RadiantElement {
	override connectedCallback() {
		super.connectedCallback();

		this.dispatchEvent(
			new ContextRequestEvent(themeContext, (theme) => {
				this.textContent = `Theme: ${theme.mode}`;
			}),
		);
	}
}
```

Pass `true` as the third argument to subscribe. The callback then also receives an `unsubscribe` function and runs again on every `setContext`. Call `unsubscribe` when the element disconnects.

```typescript
import { ContextRequestEvent } from '@ecopages/radiant/context';

import { themeContext } from './theme-provider';

export class ThemeBadge extends HTMLElement {
	private unsubscribe?: () => void;

	connectedCallback() {
		this.dispatchEvent(
			new ContextRequestEvent(
				themeContext,
				(theme, unsubscribe) => {
					this.unsubscribe = unsubscribe;
					this.textContent = theme?.mode ?? '';
				},
				true,
			),
		);
	}

	disconnectedCallback() {
		this.unsubscribe?.();
		this.unsubscribe = undefined;
	}
}
```

A Radiant provider answers a `context-request` this way:

- It calls `stopImmediatePropagation()` before the callback, so the nearest provider answers and a throwing callback cannot reach an outer one.
- It calls the callback at once with the current value. A provider with no `initialValue` and no `setContext` yet passes `undefined`, as Lit's `@lit/context` does. A subscriber also gets its `unsubscribe` at once, and receives the first value when it is set.
- Without `subscribe` it calls the callback once and keeps no reference to it.
- It reads only the protocol fields (`context`, `callback`, `subscribe`), so an event from another library, or a plain `Event` with those fields, works too.

`ContextRequestEvent.handled` becomes `true` when a provider stops the event's propagation, which tells you whether any provider, Radiant or not, answered.

`@contextSelector` and `@onContextUpdate` can also be answered by a provider from another library. They ask Radiant providers first and send a protocol `context-request` only when none answers, so in a tree that mixes libraries a Radiant provider further up wins over a nearer foreign provider of the same context. `@consumeContext` needs a Radiant provider: its field holds the `ContextProvider` instance, which a protocol provider does not hand out.

`ContextSubscriptionRequestEvent`, `ContextProviderEvent` and `ContextEventsTypes` are also available from `@ecopages/radiant/context`.

`ContextProviderEvent` is the late-provider announcement a provider dispatches when it upgrades (`context-provider`; an `Event` with `context` and `contextTarget`, bubbling and composed). It is the same event Lit's `@lit/context` dispatches and its `ContextRoot` listens for, not part of the protocol itself. `@consumeContext` and `@contextSelector` listen for it; a manual requester that should survive a provider defined after it can listen on its own ancestors and dispatch its request again when `event.context` matches. Only a provider announces itself: the manual request above is not retried for you.
