# Slots

`<slot>` in `render()` places a render-owning `RadiantElement`'s children. How they arrive decides how `<slot>` resolves, with one exception for hosts the server rendered outside every host's view (see [Server-rendered hosts](#server-rendered-hosts)):

- **From a JSX view.** When a view renders `<x-card>{children}</x-card>` and `x-card` is defined and overrides `render()`, the view hands a **Children Value** to the host. `<slot />` renders that value, and the host's renderer is the only one that touches the resulting nodes. Named regions are properties.
- **As HTML.** Children written in markup, created with DOM APIs, rendered before the tag was defined, or rendered on the server in a page outside every host's view or in plain mode become **Authored Children**. They are captured once, when the host first renders, and assigned to slots by their `slot` attribute.

## Children Value from a JSX view

```tsx
/** @jsxImportSource @ecopages/jsx */

import type { JsxRenderable } from '@ecopages/jsx';
import { RadiantElement, customElement, state } from '@ecopages/radiant';

@customElement('x-card')
export class XCard extends RadiantElement {
	@state header: JsxRenderable = null;
	@state open = true;

	override render() {
		return (
			<section class="x-card">
				<header>{this.header}</header>
				{this.open ? (
					<slot>
						<p>Nothing here yet</p>
					</slot>
				) : null}
			</section>
		);
	}
}
```

```tsx
<x-card header={<h2>{title}</h2>}>
	{items.map((item) => (
		<p key={item.id}>{item.label}</p>
	))}
</x-card>
```

- `children` fills the default `<slot />`. Its fallback renders while the children are empty.
- A named region is a property, rendered with `{this.header}`. An unprefixed name binds as a property on a custom element; write `prop:name` only for a name that binds as an attribute by default, such as `title` or `id`.
- Every render of the view passes the **Children Value** again and the host renders it in place, so adding, removing or reordering children, and binding updates inside them, show up even when the host hid its `<slot />` meanwhile.
- `slot="name"` on a JSX child does not select a named slot: the child stays in the default slot, and development builds warn to pass it as a property. A `<slot name="…">` in such a host renders its fallback.
- Nodes appended to the host with DOM APIs remain outside its projected slot content; development builds warn to change the children in the view instead.
- On the server, a host builds its children inside its own context providers, so a consumer passed as a child of a provider host resolves that provider. In hydrate-mode SSR, a host inside another host's view renders the children itself and waits on the client for that view to hand them back, so define the parent host on the client as well. Plain-mode SSR does not make the host wait, and its parent may never be defined on the client, so it renders them as **Authored Children** with a slot-projection payload, and the host still renders them when its parent is not defined.

A custom element that is not a Radiant host, or a Radiant host without a `render()` override, keeps its JSX children as DOM nodes inside it.

## Authored Children

```tsx
/** @jsxImportSource @ecopages/jsx */

import { RadiantElement, customElement } from '@ecopages/radiant';

@customElement('shell-card')
export class ShellCard extends RadiantElement {
	override render() {
		return (
			<section class="shell-card">
				<slot name="heading">
					<h2>Fallback heading</h2>
				</slot>
				<div class="shell-card__body">
					<slot>
						<p>Fallback body content</p>
					</slot>
				</div>
			</section>
		);
	}
}
```

```html
<shell-card>
	<h2 slot="heading">Projected heading</h2>
	<p>Projected body content</p>
</shell-card>
```

- Slots are resolved from direct host children.
- The default slot receives direct host children without a `slot` attribute.
- Named slots receive direct host children whose `slot` attribute matches the slot `name`.
- Fallback JSX inside `<slot>` renders only when no matching projected content exists.
- Nodes appended to the host after its first render are projected too.
- SSR host rendering serializes the projected content and embeds the metadata needed to reconstruct slot assignments on the client.

A tag defined only after a view rendered it treats those JSX children as **Authored Children**, and development builds warn: the host then does not follow later edits the view makes to them. Define custom elements before rendering views that use them.

### Server-rendered hosts

What the server rendered decides how a server-rendered host takes its children on the client. In hydrate mode, a host the server renders outside every host's view gets **Authored Children**, ships them in a slot-projection payload, and is stamped `data-radiant-ssr="authored"`. It keeps those children for its lifetime and ignores any **Children Value**: when page-level JSX hydrates over it, its named slots stay as the server rendered them, a later render of the page JSX does not change them, and event bindings in them never attach. Render changing or interactive content inside a host's view, or pass it through a property. The page's hydration keeps the host's node when the tag was defined before the page JSX was created; otherwise the host is rebuilt and takes those children as **Authored Children**.

A host the server renders inside another host's view in hydrate mode, and any host that client JSX creates while its tag is defined, takes the **Children Value**. Plain-mode markup carries no stamp and no hydration markers, so page JSX renders over it instead of hydrating.

## View helpers

A view helper that owns the shell can also put chrome and children in the **parent tree**: named helpers or props occupy a region, and the custom element queries `data-ref` / `data-*` and paints with [@bindTo](/docs/decorators/bind-to) instead of rendering a `<slot>`. Radiant UI composes its parts this way.

```tsx
<RuiDialog title={<>Edit plant</>}>Body</RuiDialog>
```

See the authored light-DOM host in [RadiantElement](/docs/components/radiant-element) and the Radiant UI composition guide.

## Querying Assigned Content

Use [@querySlot](/docs/decorators/query-slot) when component logic needs the assigned elements for a default or named slot. On a host that receives a **Children Value**, the default slot's elements are the top-level elements that value rendered to, and named slots are empty.
